# SCR-002: define supported rename-pair reporting

- Raised by: W5-A Date: 2026-10-11
- Affects: RawEvent/watch event contract; Docs: 07 §3.4, wave-5-live W5-A
- Affected tasks: W5-A, W6-A

## Problem
07 §3.4 requests explicit from→to rename pairs, but its selected MOVED_FROM/MOVED_TO events have no correlation cookie in the frozen RawEvent payload. Pairing by PID or adjacency is ambiguous when multiple writers rename concurrently. RawEvent::Fid carries one handle/name, and the existing watcher outputs only aggregate rows. The local UAPI header also defines FAN_RENAME with OLD_DFID_NAME and NEW_DFID_NAME information records (types 10 and 12), requiring a two-location event shape and separate capability negotiation.

## Proposal
For kernels supporting only the specified MOVED_FROM/MOVED_TO masks, officially report directional counts/deltas without claiming exact pairing. If exact pairs are required, add a separately probed FAN_RENAME capability and a RawEvent rename variant containing both directory handles and names; define a corresponding bounded watcher output and retention policy. Preserve existing fd-mode degradation.

## Impact if accepted
Sys decoding and watcher event delivery can represent both locations without guessing. Daemon/API/persistence consumers need an explicitly decided pair shape if pairs are exposed beyond foreground output. New reporting must remain behind a runtime probe on EL8.

## Interim
Existing masks and frozen RawEvent fields are preserved. Move directions are aggregated independently, with estimated removal/addition deltas and handle-path cache invalidation. Exact rename pairs are not implemented.
