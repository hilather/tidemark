# SCR-002: Walker record byte budgets and publication collision ownership

- Raised by: W2-C    Date: 2026-10-11
- Affects: WalkConfig and SnapshotWriter publication API    Docs: 04 §7; 05 §2
- Affected tasks: W1-B, W1-E, W2-A, W2-C

## Problem
WalkConfig exposes candidate bounds but no byte budget for links/skips/errors in a record. The walker allows up to one million entries per record. A bounded channel and exact candidate reservation do not themselves bound all queued/producer allocations to scan.memory_budget. W2-C reserves a 1 MiB additional record allowance and 64 MiB base estimate, but these estimates are not worst-case limits for a link-heavy record or a very large aggregator. Reserving all worst cases would reject the default configuration even for tiny trees.

Also, Prepared::write consumes Prepared, and SnapshotWriter::finish consumes the writer. The writer refuses a publication collision, but after that failure W2-C has neither the prepared rows nor the temporary database with which to republish under a fresh id. W2-C retries id selection and writer creation collisions safely, but cannot retry a collision occurring during finish without restarting the entire scan.

## Proposal
Agree a walker record byte cap and a scan-wide bounded allocation policy, e.g. new WalkConfig fields record_memory_budget and producer_memory_budget, with typed resource errors on breach and explicit accounting for queued records. W2-A should expose/obey its agreed budget too. For publication, retain the built writer on an AlreadyExists result or let the store accept an agreed fresh-id retry callback and update meta.scan_id atomically before publishing. Exact signatures must be agreed across owners.

## Impact if accepted
Walker, aggregator, store and orchestrator implement coordinated accounting and publication retry. No frozen schema change is needed. An allocation-policy decision may affect legal scan configuration and needs explicit coordinator review.

## Interim
Candidate channel budgeting includes top-N, the documented 4096 threshold candidates, 255-byte names, allocation/capacity overhead, producer heaps/buffers, and bounded queue capacity (1–64). Resource refusal is explicit when these reserves do not fit. Additional record/base storage remains an estimate. Existing snapshot files are never replaced; creation collisions retry, publication collisions safely fail. These limitations are listed as incomplete in the handoff.
