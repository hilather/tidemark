# SCR-001: Pass the installed config destination to deployment commands

- Raised by: W4-B    Date: 2026-10-11
- Affects: CLI global `-c` destination and shared `Context` contract. Docs: 08 §1/§5; stage Args rustdoc.
- Affected tasks: W0-B2, W4-B, W6-A

## Problem
`cmd::deploy::stage::Args::from` documents that global `-c` names the installed path, but shared `Context` holds only parsed configuration, json and color. Command dispatch discards the path. The frozen stage signature cannot recover the destination from the parsed Config. Global configuration validation also occurs before deploy stage dispatch, so an invalid currently installed config can prevent staging a valid replacement.

## Proposal
Add `pub config_path: PathBuf` to shared `Context`, populate it from the global CLI path, and pass it to `RealEnv`. Permit `deploy stage --from` to validate its source even if the installed config is invalid; keep its blocking failure exit 5.

## Impact if accepted
Coordinator updates the shared Context construction sites and loading path. W4-B stage adapter switches its installed destination to `context.config_path`. No new flags or config keys.

## Interim
Library Env supports explicit destinations and is tested on temporary paths. Production command adapter retains `/etc/tidemark/tidemark.toml`; nondefault global `-c` destination support is unresolved. No process-argument reparsing workaround or shared-file edit was introduced.
