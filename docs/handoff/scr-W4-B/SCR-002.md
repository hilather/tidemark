# SCR-002: Clarify the guarantee after a runtime deployment failure

- Raised by: W4-B    Date: 2026-10-11
- Affects: deployment failure semantics. Docs: 08 §5; ADR-016; wave-4 W4-B.
- Affected tasks: W4-B, W6-A, rollout gate

## Problem
The pre-flight guarantee is precise: a blocking failure changes nothing. The runbook's shorthand also says every nonzero staging exit means nothing changed. Once configuration replacement, systemctl enable/restart, and durable record publication begin, they are separate operations without a shared transaction. A service restart cannot be made unobservable, and a filesystem or systemctl failure can also prevent compensation. Atomic rename followed by a failing directory fsync can have already published its file.

## Proposal
Keep zero side effects for all blocking pre-flight failures. For failures after successful pre-flight, specify best-effort compensation of config/record bytes and previous enable/active state; report both the initiating error and any compensation errors. Explicitly document that transient restarts, timestamps/permissions and newly created empty directories may remain. Operators must inspect the error and retry or unstage rather than treating every nonzero runtime exit as a successful rollback.

## Impact if accepted
Clarify 08 §5 and rollout shorthand, retaining existing flags and exit codes. No contract type or shared-file change is needed.

## Interim
The implementation restores previous config/staged/marker bytes, removes newly made config backups and attempts to restore service enable/active state. Fake tests inject enable and record-publication failures. It does not claim transactionality across systemd and the filesystem. Blocking pre-flight failures still have zero writes and zero service mutation calls, explicitly tested.
