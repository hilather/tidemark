# SCR-003: Define which filesystem types prove a root is local

- Raised by: W4-B    Date: 2026-10-11
- Affects: deployment pre-flight eligibility. Docs: 08 §5 roots check.
- Affected tasks: W4-B, rollout gate

## Problem
The blocking roots check says “local filesystem” without a classification policy for unknown or unusual mountinfo filesystem types. A denylist of NFS/CIFS would admit unrecognized network/FUSE types. A local-type allowlist fails closed but can also reject uncommon genuinely local types. Mountinfo alone does not prove locality of arbitrary FUSE implementations.

## Proposal
Specify a v1 recognized-local allowlist (currently xfs, ext2, ext3, ext4, btrfs, tmpfs, zfs, f2fs, jfs, reiserfs), and state that unknown types block until reviewed. Alternatively, provide an expanded normative classifier and fixtures, including the intended overlay/FUSE policy. No config key or CLI flag is requested.

## Impact if accepted
Document the pre-flight eligibility rule in 08 §5. The target Rocky/XFS hosts are covered. Additional local filesystem types need explicit additions and test fixtures.

## Interim
Production pre-flight implements the conservative list above and explains unsupported types. It does not infer locality from an arbitrary device/source string. Fake pre-flight tests exercise both local and rejected root outcomes without depending on the worker's mounts.
