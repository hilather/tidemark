# SCR-001: Allow crate-private streamed snapshot access

- Raised by: W3-B    Date: 2026-10-11
- Affects: store reader implementation API   Docs: wave-3-queries W3-B
- Affected tasks: W3-B, potentially W3-A and W3-C

## Problem
`Snapshot.conn` is private to `reader.rs`. Its public directory, link-set and
instance queries return complete vectors, with a one-million-row cap. W3-B owns
only `links.rs`, and cannot expose a streaming connection or query in reader.rs.
The required inode-ordered streaming implementation cannot be built using these
frozen methods. Fetching each set's instances separately also requires a query
per set and prevents confident performance acceptance at one million sets.

## Proposal
Coordinator adds this crate-private accessor in `reader.rs` without changing any
public or core contract:

```rust
pub(crate) fn connection(&self) -> &rusqlite::Connection { &self.conn }
```

W3-B can then stream directory interval rows and `link_sets LEFT JOIN
link_instances` ordered by inode, with bounded retained sets/pairs, instead of
using vector-returning queries. Keep `link_sets_under` for CLI boundary selection.

## Impact if accepted
Only the store reader needs a shared-file edit. No schema, CLI or core migration.
W3-B needs follow-up work to implement streaming and measure the million-set gate.

## Interim
Implemented bounded queries through the existing reader, processing instances
one set at a time. All vector/map limits are explicit; excess fails. This is an
interim implementation and does not satisfy the streamed-row acceptance item.
No reader or shared-file edits were made.

## Interim measurement
`cargo test -p tidemark-store --test w3b million_set_report_timing -- --ignored
--nocapture` measured 85.079075606 seconds for the report (debug build, Intel
Core i7-8750H, sandbox). The timing assertion failed; one million crossing sets
were counted correctly. Snapshot setup was outside the measured interval. This
is not a passing CLI performance gate or a release-build measurement.
