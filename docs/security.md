# Tidemark security model

Tidemark observes filesystem allocation, directory entries, links, open-file metadata and storage capacity. It is designed for Rocky Linux 8 / XFS on LVM. Its scanning and watching code is designed to inspect metadata without reading regular-file payloads or modifying scanned data; the current boundary and atime limitations are stated below. It does not manage mounts or change LVM configuration. It stores its own snapshots and measurements, exposes a local Unix API, and can publish a metrics textfile. Explicit deployment commands also write Tidemark configuration and service enablement.

This document derives from the second [security audit](reviews/W7-C1-audit2.md), corrected by STATE-trust-A/A2/B, AUDIT-procfs-budget, DAEMON-polish, GATE-fix, SYMLINK-atime, CLI-polish, WATCH-fsmark and CI-deny-required. These notes establish implementation evidence; independent review and guest acceptance remain separate. The decision record is [R5](plan/13-contract-decisions.md#hardening-second-guest-runs-and-wave-7-decisions).

## Trust and privilege

The installed `tidemarkd` service runs as root to observe protected directories and processes. Its capability bounding set contains exactly:

| Capability | Purpose |
|---|---|
| `CAP_SYS_ADMIN` | XFS bulkstat and fanotify initialization/mount observation on supported EL8 kernels. |
| `CAP_DAC_READ_SEARCH` | Traverse and inspect protected directories; open-by-handle metadata access in FID and fd/filesystem modes. |
| `CAP_FOWNER` | Open foreign-owned directories with O_NOATIME. Without it, the EPERM fallback can update directory atime. |
| `CAP_SYS_PTRACE` | Pass procfs access checks for other processes' fd/identity metadata. Tidemark does not attach to or trace those processes. |

Removing one of these capabilities from the current service can reduce measurement coverage or its no-atime behavior. They are substantial powers: a compromised root daemon is not confined to harmless metadata observation. A future privileged helper split would require separate design and testing.

The unit sets NoNewPrivileges, a 2 GiB memory limit for either supported cgroup generation, CPUQuota 200%, NOFILE 65,536, native syscall architecture, and namespace/realtime/personality restrictions. Its address-family allowlist is `AF_UNIX`. It intentionally does not create a private mount namespace: fanotify marks must observe the server's real mount objects. Do not add namespace-creating systemd hardening settings without validating watcher behavior. The unit is not a read-only filesystem sandbox.

Tidemark trusts the kernel, host procfs/sysfs, local filesystem implementation, installed binaries/libraries and reporting tools, root-controlled configuration, and administrators with mount or equivalent privilege. Another root process or an attacker controlling those components can defeat its invariants. Processes' comm/cgroup strings are labels, not authentication identities. Concurrent filesystem and process observations are best-effort measurements, not a transactional forensic record.

## Access and sudo

Production access is root only (ADR-018). There is no Tidemark access group. Administrators run the CLI with sudo; a filesystem permission error is not a reason to grant group access to the socket or snapshots. Default runtime and state directories are root-owned 0700, the API socket is 0600, and private state/configuration artifacts are intended to be root-owned with no group/world access. The metrics export is the deliberate exception described below.

The server validates socket ancestors, binds through a retained directory, checks socket/lock identities, and authenticates uid 0 using kernel SO_PEERCRED before parsing requests. Application authorization remains root only even if socket permissions are accidentally broadened. The library can operate on effective-user-owned temporary state for unprivileged fixtures; this does not change the production access policy.

Sudo authority should match the administrator's intended trust. Granting arbitrary Tidemark arguments includes selecting configuration/state/output paths and invoking deployment/purge functions; do not treat an unrestricted Tidemark sudo rule as a harmless read-only privilege. Use the installed absolute executable and trusted configuration, and avoid user-controlled environment or writable ancestors. Where delegation is necessary, constrain commands and arguments through the site's existing sudo policy. Do not use user-owned preseeded state.

## Information sensitivity and communications

Snapshots, catalog rows, process reports, metrics and logs can reveal raw file/path names, storage layout, process identities and activity. Names alone may disclose database, customer, backup or project information even though regular-file contents are never intentionally read. Protect state and backups with root-only ownership/access and the site's retention controls; SQLite snapshots are not encrypted by Tidemark.

Human result renderers escape control characters, backslashes and invalid UTF-8 in filesystem/process names. Printable Unicode can remain visually misleading. Deployment and final error diagnostics escape embedded controls while preserving renderer-owned line breaks (CLI-polish). Treat decoded machine output as untrusted. JSON uses proper JSON escaping and byte-path base64 fields where required. These are machine encodings: decoded JSON strings must not be interpolated into shells or terminals. Prometheus label encoding escapes quote, backslash and LF but does not make arbitrary label text terminal-safe.

The metrics textfile is published with mode 0644 for a collector. Its contents and the collector's network access are an explicit confidentiality decision: use a trusted collector directory and restrict downstream exporter/scraper access as appropriate. Tidemark does not provide a separate v1 redaction key. Journal access is governed by host journal permissions and retention; structured fields avoid newline-based field injection but do not make names nonsensitive.

ADR-020 removed HTTP, TLS listeners/clients and webhooks from v1. No webhook payload is sent, and no webhook/TLS configuration remains to secure. The only application listener is the local Unix API. Outbound Unix sockets are also used for journald and systemd notification, and Unix connection probes test the API socket. The unit allows only AF_UNIX; GATE-fix reports LVM reporting measurements on both supported Rocky releases without address-family errors. A separate node exporter may serve the metrics file over its own network endpoint; that service is outside Tidemark's API boundary.

## Read-only behavior and its limits

Walker and bulk scanning use directory entry enumeration and stat/ioctl metadata, no-follow component opens, filesystem/mount checks and bounded iterative traversal. Symlink analysis reads link text, not its referent's payload. Process inspection reads specific numeric procfs metadata paths, fdinfo and symlink targets; it does not open `/proc/PID/fd/N` for data. Active watches retain a directory descriptor on the mount for event/path identity, preventing ordinary unmount until watcher teardown; lazy detach leaves the old filesystem busy until the daemon notices and releases it. Watcher reads are from the fanotify notification-group stream. Delivered event descriptors are only inspected for metadata/path identity and closed unread; FID resolution uses O_PATH handles. LVM collection runs reporting-only `lvs`/`vgs` commands and never uses LVM mutation commands or the misleading `--readonly` option that hides thin-pool usage.

Configuration, Tidemark's own SQLite/JSON state, kernel procfs/sysfs, host OS identity and loader/runtime files are legitimate regular or pseudo-file reads. They must not alias scanned payloads. State snapshots can use SQLite mappings; a grep for Rust read calls alone cannot establish the global property. Scanning's metadata syscalls are subject to the Gate, and worker directory opens request O_NOATIME with a charged EPERM retry where needed. No user-supplied command is interpolated into a shell for storage observation.

The source gate in `xtask/src/checks.rs`, run by `cargo xtask ci`, rejects specified forbidden mutation symbols/commands. First-party unsafe is confined to reviewed `tidemark-sys` wrappers, with ABI/layout and parser/descriptor tests. These checks reduce mistakes; they are not a general proof of syscall behavior. The guest strace design in the second audit tracks fd provenance, inode aliases, dup/fork, fanotify-delivered fds and file mappings; its required assertion is zero attempted payload reads and explicit unread event-fd closure. That new regression design has not yet been implemented or run by this audit. Privileged XFS/fanotify/fault and cumulative fuzz gates remain required release evidence.

### State, directory and leaf trust

Storage opens absolute paths component by component with no-follow directory descriptors, refusing parent traversal and symbolic links. In packaged builds, ancestors must be owned by root or the invoking effective user, with no group/world write unless sticky with an owned child without group/world write; sticky chains propagate that rule. Neither user-namespace overflow ownership nor read-only mounts waive ownership. Symbolic links anywhere in the state path are refused: configure the real path, and expect `Not a directory` at a refused link. Development builds allow the overflow-uid and read-only-mount ancestry exceptions, announce them once per process, and enforce strict rules with `TIDEMARK_STRICT_ANCESTRY=1`.

State directories and used subdirectories must be euid-owned and not group/world writable. Leaves must also be regular, single-link and euid-owned. Storage integrity permits group/world readability, issuing one process-wide warning for the first readable accepted path; new directories/leaves remain 0700/0600. This storage allowance is not a change to production root-only access. Checks cover SQLite main files, WAL/SHM/journal and v0 backups/sidecars, snapshot temporaries and scan.lock before header reads or SQLite use. Nonblocking no-follow leaf opens refuse FIFOs promptly. Retained descriptor-relative anchors prevent unprivileged ancestor substitution; SQLite pathname opening still assumes no hostile root/same-euid replacement between inspection and use.

Daemon/deployment admission additionally requires private configured state. A checked deployment marker permits normalizing existing read/execute bits to 0700 only after ownership/no-foreign-write checks; it never permits chown or waives ownership. Deploy children stay private even with a marker. Unsafe preexisting paths/content are refused, never repaired as a trust bypass. Metrics collector ancestry uses the same shared trusted-directory rule, checked each export pass before staging writes. The API keeps its separate stricter private sticky-child policy and locks `<socket>.lock`; exporter locks `<textfile>.tmp`, never a directory.

### Access-time and mount limits

`tidemark symlinks` reads link text and may update that link's access time, subject to mount atime policy. No scan and no other command reads the text of symbolic links it finds. Resolving a path supplied on the command line follows links in that path through canonicalize as ordinary tools do. `--check-targets` resolves components with gated no-follow operations and stops before external metadata/link text at the selected mount boundary, including same-device bind mounts; `OtherFs` means the external target was not checked. The 40-expansion limit can report Loop for long chains as well as cycles. O_NOATIME EPERM fallback can update directory atime. Tidemark never remounts or restores timestamps to conceal such effects.

On measured EL8 kernels statx lacks mount IDs. Mountinfo/fd identity checks reduce crossings, but a new same-device, same-inode bind after a mount snapshot may be indistinguishable. Trusted host mount administration remains part of the boundary. fd/filesystem uses filesystem marks on supported Rocky 8.10 and maps foreign-mount events by handle; fd/mount on 8.8 cannot see writes through other bind mounts/private namespaces. Unmappable events retain totals and fall back to the watched root for directory attribution. Full restricted-unit filesystem-mark and symlink-boundary guest acceptance is pending.

## Availability

The API limits active connection workers and request/response bytes, uses absolute frame/write deadlines, retains handler ownership and backs off on descriptor/memory accept pressure. Default directory/socket permissions and peer authorization exclude unprivileged slow API clients. Kernel or SQLite calls can still delay completion; handler ownership does not imply interruptible I/O.

Watcher reads have a descriptor budget per mount; the 512-descriptor daemon reserve is feasible only when the soft limit is at least `512 + 16 × mount_count`. Below that, the code warns and still uses the minimum batch. Overload becomes loss/degradation with bounded backoff. Rings, caches, dirty paths and foreground queues have count caps. Walk and bulk work use count/byte caps and explicit errors rather than claiming a complete truncated result. A local user can still create workloads that make measurements lossy, expensive or unable to complete.

Count caps are not a whole-process memory reservation. Process inventory has a 128 MiB per-pass budget for target capacities, record-vector allocation (including reallocation overlap), and an 8 MiB numeric-ID allowance. Exceeding it returns a typed budget error and fails the pass, never publishes a truncated inventory. Downstream process working allocations have separate fallible budgets; AUDIT-procfs-budget gives a conservative envelope below 512 MiB, not a whole-process RSS guarantee. DAEMON-polish reports typed OutOfMemory as degraded with counts/bytes; failed measurements remain unavailable to alerts. Guest load testing and real second-user trust acceptance remain pending. Service restart is recovery, not protection against hostile workload denial of service.

## Deployment safety

`deploy stage` captures bounded no-follow regular configuration bytes, validates those exact bytes, hashes them and installs that same version. Blocking preflight checks happen before service/configuration changes; documented capability warnings alone can be skipped. Stage checks state locality, roots, mounts, space and deployment state. Config/state publication uses temporary files, sync and rename with retained handles where implemented. Source byte capture fixes the former separate-parse race.

After successful preflight, operations are not a transaction. A later failure attempts compensation for configuration, deployment record and service state, reports compensation failures, and can leave newly created empty directories or changed times. Service operations call a fixed `/usr/bin/systemctl` target without shell interpolation. Ordinary unstage stops/disables the service and removes its staged record; recursive state deletion requires the separate explicit purge guards. Purge traverses iteratively with no-follow descriptors, mount/identity checks and a depth limit. It is deliberately destructive to accepted Tidemark state, so do not grant it as read-only sudo authority.

Marker JSON identifies deployment state; its contents are not a substitute for trustworthy ownership. Stage/unstage/purge use the verified ancestry, root and marker-leaf policy above. Existing state content is checked before service mutation; marker/config matching and bounded no-follow purge traversal remain required. Hostile root/same-euid substitution remains outside this guarantee. Tidemark does not alter fstab, boot configuration, filesystem settings or LVM as part of normal observation.

## SELinux

Tidemark ships no SELinux policy and does not require a particular SELinux mode. Supplied deployment evidence reports successful Rocky 8.8 and 8.10 runs with enforcing SELinux, the four-capability unit, NoNewPrivileges and a 2 GiB limit, with no denials; the measured systemd security score was 5.9 MEDIUM. These guest results were supplied to the audit and not independently rerun. The owner's production servers do not use enforcing SELinux. Neither a supplied successful run nor permissive operation proves compatibility with every site's labeling/policy; investigate denials under the site's normal policy process rather than treating SELinux disabling as a Tidemark installation requirement.

## Supply chain and unsafe dependencies

The Rust toolchain is pinned to 1.98.0 and Cargo.lock records the dependency graph. The Rocky RPM Containerfile is a controlled build recipe with a pinned Rust/package helper version; its floating base image and repository downloads do not establish bit-for-bit reproducibility. Rebuild provenance and comparison remain necessary for that stronger claim. Build scripts, procedural macros, compiler, native libc/SQLite and OS tools are trusted supply-chain code even when they are not runtime Rust packages.

HTTP/TLS and PostgreSQL stacks are absent from the reviewed lockfile; SHA-2 remains for local configuration identity. ## Deliberate exclusions

Tidemark does not defend against root-equivalent attackers, a hostile kernel/filesystem implementation, substituted trusted binaries/reporting tools, or an administrator who grants access to private state and then expects it to remain confidential. It does not sanitize arbitrary output for downstream shell execution, provide transactional consistency over a changing filesystem, infer reliable security identity from process labels, encrypt snapshots, or guarantee uninterrupted measurement under hostile resource exhaustion. Verified state/metrics checks do not make arbitrary administrator-selected paths confidential or defend against hostile root. No PostgreSQL-specific tracking, HTTP service or webhook transport is part of v1.
