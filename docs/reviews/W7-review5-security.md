## Purge protocol and interruption analysis

Under the root-only, cooperating-process boundary, writer ownership excludes live Catalog/TimeSeries writers before any unlink. Writer then scan ordering matches scan/recovery callers. Flock retry is bounded (ten seconds for each purge phase); kernel filesystem calls and the size of a legitimate state tree are not covered by that wall-clock budget. Traversal streams width and caps depth at 256 (`purge.rs:18,100-186`), checks euid ownership/no foreign write/same mount before descending, and unlinks non-directory entries without following them. The existing unsafe-descendant, rename, FIFO and symlink regression bodies all executed in the focused purge run; the foreign-owner branch is injected, while writable modes and renames are real.

The identity recheck consists of separate syscalls, not an atomic compare-and-lock. A cooperating purge cannot unlink an existing writer lock after another writer has successfully acquired it, because purge first needs its exclusive flock. A waiter on the old, unlinked inode must wait for purge's retained flock and then fails the named/held identity checks. A new opener after the final lock unlink creates a named lock, making the single final rmdir fail; purge never resumes destructive traversal. A new lease can briefly coexist with the finalizing purge's obsolete exclusive fd, but that purger has no remaining data writer and only the single rmdir left. The executed finalization test creates a new entry or replaces the directory after lock removal and proves preservation; no claim is made that it exhaustively schedules every opener interleaving. Trusted ancestry and private deployment state exclude ordinary users replacing state or its directories. A previously exposed lock descriptor can still cause bounded Busy; changing permissions does not revoke an already held descriptor. Hostile root/same-euid mutation between checks remains outside the established boundary.

Interruption is not transactional (source inference): during data traversal, some data and possibly the marker may already be gone, but the lock names remain until the data walk finishes. Process exit releases its locks. During finalization the data walk is over and no later destructive retry occurs. Restarted code can recreate missing lock files and attempt normal startup/recovery; already deleted data is not restored, and a lost marker makes another guarded purge refuse rather than bypass admission. The command has already stopped/disabled the service before a lease refusal, so “nothing was removed” means state data, not unchanged service state. No real kill-during-purge/power-failure or durability test was run.
