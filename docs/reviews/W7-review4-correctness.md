## Lifecycle and behavior cross-checks

### Lease, startup and direct commands

Healthy startup skips busy scan ownership without waiting (`crates/tidemarkd/src/lib.rs:1459-1460`) and acquires shared writer ownership alongside existing writers. An exclusive holder can make an ordinary writer wait up to two seconds (`crates/tidemark-store/src/lease.rs:69-73`), then return the explicit recovery refusal. Corrupt/missing/uninitialized startup first waits up to 30 seconds for exclusive writer ownership, then starts a separate 30-second scan-lock deadline (`lib.rs:1431-1457`): roughly 60 seconds is the code's combined contention bound, plus actual filesystem/SQLite work; this is not a measured typical delay. Busy returns “state directory in use by another tidemark process”; it is not pressure-retried. Typed EMFILE/ENOMEM pressure retries at 50–800 ms backoff until shutdown (`lib.rs:902-945`). The two new pressure regressions test both error seams and real child-local descriptor exhaustion.

The waits do not accept/check the shutdown flag. A SIGTERM during recovery contention can therefore leave startup waiting the remaining phase duration. The nine-second runtime join deadline starts later; `join_until` still joins after reporting expiry (`lib.rs:1390-1407`). The service has no explicit `TimeoutStopSec`. Source proves eventual descriptor release after normal join, not a universal ten-second kernel-operation bound. A cancellable single overall startup deadline would improve this behavior; no production start/signal timing was measured here.

The once-per-second scheduler open is **read-only** (`scheduler.rs:1343-1345`) and has no writer lease. Per source, each open repeats verified ancestry/directory traversal, DB plus seven companion checks twice, another existing-leaf check, a 16-byte state-DB header read, and SQLite open/version work (`catalog.rs:120-130`, `timeseries.rs:69-138`). This reads only Tidemark's own database. No per-open latency benchmark was run. A long-lived time-series writer plus catalog hold two shared leases (`services/tswriter.rs:129-131,267-268`), so an exclusive recovery holder cannot appear while that healthy worker retains them.

After actual writer-thread exit/unwind, its leases drop and the supervisor retries with 5–300-second backoff. An exclusive holder can acquire in that gap. A held lease alone leaves read-only scheduling usable and writer reopen retrying until release. **Inferred interleaving:** actual database replacement in that gap can race the scheduler's existing-file/header open (Io NotFound) or expose new user_version=0 (Invalid uninitialized), neither classified as pressure. `scheduling_catalog` returns fatal and `SchedulerExit` sets global shutdown. SQLite CANTOPEN itself is pressure-retried; it is not the claimed fatal case. This full supervisor/recovery/scheduler race has no regression or reproduced whole-daemon run here. A retained daemon lifetime shared lease, or recovery-aware shared exclusion/retry for scheduler reads, would close it. Do not interpret writer lifetime tests as a daemon-lifetime recovery guarantee.

Direct scans check definitive socket absence before offline preparation and under scan ownership; scan catalog ownership now precedes ScanLock (`crates/tidemark-cli/src/cmd/scan.rs:159-184,361-413`, `crates/tidemark-scan/src/orchestrator.rs:123-124`). Prune/rebuild take writer ownership before scan ownership and repeat endpoint checks (`cmd/snapshots.rs:70-101`). Healthy same-state pre-API operations can coexist as shared writers, with scan serialization; corrupt replacement cannot displace them. Indeterminate endpoint access remains refusal. Listener/backlog and permission variants require their respective capable runners; socket-free pre-API tests exercise the missing-startup-window protection locally.
