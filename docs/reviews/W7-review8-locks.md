**SHOULD-FIX — pathname checks do not bind SQLite's open to the checked header.** Ref: `finding:w7-review8-locks-preflight-race`. Location: `crates/tidemark-store/src/timeseries.rs:107`, `:118`, `:121`; `docs/plan/05-storage.md:170`.

Concrete scenario: a read-only opener reads inode A's header and passes the identity check at line 107. Another process performs catalog recovery and replaces the named database with inode B before line 118. Read-only opens carry no writer lease (`timeseries.rs:309`), so the recovery lease does not exclude this opener. SQLite opens B before any non-SQLite read of B's header. The subsequent pathname check detects the replacement and returns an error, but cannot undo the fact that SQLite already opened an unchecked existing file. Thus the literal section 4 rule is met for stable files and replacements completed before acquisition, but is not guaranteed across concurrent replacement.

This is an inherited preflight/open race, narrowed but not eliminated by the new checks. Normal recovery creates an empty/valid replacement; I did not establish corruption from that sanctioned scenario, hence no BLOCKER. Binding the actual SQLite open to the preflight inode, or excluding replacement throughout admission for readers as well as writers, needs consideration. Another pathname stat alone cannot prove that binding. The existing replacement test (`tests/locks.rs:50`) replaces the file before the attempted open and does not exercise this interval. More elaborate owner-driven A-to-B-to-A swaps can also evade both pathname checks; no ordinary recovery path restoring A was found.

**NOTE — a descriptor can still close before registration on exceptional admission failure.** Ref: `finding:w7-review8-locks-failed-admission`. Location: `crates/tidemark-store/src/timeseries.rs:234`, `:235`, `:243`; `crates/tidemark-store/src/state_dir.rs:436`, `:438`.

Concrete scenario: inode B already has a registered live connection. Acquisition stats an unregistered inode A at the requested name; an owner-side rename substitutes B before `open_leaf` opens it. If B's permissions become group-writable after the preliminary check but before the descriptor's `fstat` validation, line 438 rejects it and drops the descriptor before it reaches the registry. The close releases the process's locks on B. An unlink causing a zero-link validation failure, or a metadata syscall error before insertion, has the same early-close shape. Retaining a successfully returned duplicate at line 243 does not cover these failures.

This does not demonstrate a daemon fault during its normal lifecycle: recovery preserves main files by rename, and I found no normal product path making the required concurrent main-file permission/unlink mutation. The registry's protection should therefore be described with that boundary, rather than as covering every conceivable failed raw open. If such replacement/error tolerance is required, raw admission must transfer ownership into lock-aware retention before fallible post-open checks can drop the descriptor. This note does not propose bypassing the trust checks.

For stable registered inodes, each call still performs positioned reads of the first 16 bytes before SQLite (`timeseries.rs:104`, `:256`); it does not cache a previous header verdict. Invalid nonempty headers return `SQLITE_NOTADB`, and empty files remain admissible. A replacement already present when acquisition begins has a different identity and gets its own header descriptor. Retaining the old descriptor also prevents inode-number reuse while that registration is live.

The relevant kernel rule is process-wide: an independent close releases POSIX locks for that inode even when another descriptor owns the live SQLite connection. SQLite documents both that hazard and its internal close coordination in [How To Corrupt An SQLite Database, section 2.2](https://sqlite.org/howtocorrupt.html#posix_advisory_locks_canceled_by_a_separate_thread_doing_close_).
